# Handoff: routines / scheduling / automations

You're picking up the next big feature in smart-home-os. Read [CLAUDE.md](../CLAUDE.md) first. It covers the topology, building and deploying, the gateway and agent internals, and the verification rules. This doc covers only what's specific to this work. The roadmap entry is "Scheduling / routines / triggers / automations" under HIGH PRIORITY in [docs/todo.md](todo.md).

## Goal

Make the platform automate things on its own. A user creates a **routine** in the Routines tab: one or more **triggers**, optional **conditions**, and an ordered list of **actions**. It runs unattended and leaves a record of what happened.

Example routines the design must handle:
- "Weekdays at 7:00, fade the bedroom lights up over 10 minutes and play my morning playlist on Bedroom Speakers."
- "30 minutes after sunset, turn on the living room lamp group."
- "When the front door sensor opens and it's after 22:00, turn on the hallway light."
- "Every night at 23:30, turn everything off."

## What already exists (verify before relying on it)

**Time and location**
- `home_profile` is a singleton (`Home` in [shared/database/models.py](../shared/database/models.py)). It has `timezone` (set from NWS during geocoding) and `latitude`/`longitude` as `Numeric(9,6)`.
- That's enough to compute sunrise/sunset locally. A small pure-Python sun calculation, or a light library such as `astral`, needs no network.

**Device and group control**
- The gateway exposes the control endpoints in [services/gateway/api/routes.py](../services/gateway/api/routes.py):
  - `POST /api/devices/{device_id}/set`: an RPC that resolves on the device's next state publish, with a 5s timeout.
  - `POST /api/groups/{friendly_name}/set`: fire-and-forget.
- Both translate between IEEE address and friendly_name (see CLAUDE.md).
- A scheduler running inside the gateway should call the same internal logic as these endpoints, not loop back over HTTPS.

**Device state changes (for triggers)**
- `AsyncMqttBus` in [services/gateway/core/mqtt_bus.py](../services/gateway/core/mqtt_bus.py) handles every Z2M message. `bus.subscribe()` returns an `asyncio.Queue` of updates, which is what `/api/ws` uses.
- The Redis twin `gateway:digital_twin` (keyed by IEEE) has current state for condition checks.
- The bus is created in the FastAPI `lifespan` in [services/gateway/main.py](../services/gateway/main.py). That's where a scheduler task would start and stop.

**Spotify**
- All Spotify logic, including per-user token refresh, lives in the **agent**: [services/agent/tools/spotify_service.py](../services/agent/tools/spotify_service.py). The gateway has none of it.
- The always-on speaker "Bedroom Speakers" (Spotify Soloist on the Pi, see section 11 of [docs/raspberry-pi.md](raspberry-pi.md)) stays in `/me/player/devices` while idle. Playback can be started by name with no phone open. This is what makes music routines possible.

**Agent**
- The gateway reaches the agent at `http://agent:8001` (hard-coded proxy in `main.py`).
- The agent authenticates by decoding the user's JWT (shared `JWT_SECRET_KEY`).
- So the gateway can mint a short-lived JWT for a routine's owner and call the agent, the same way the agent mints JWTs to call the gateway in [tools/gateway_api.py](../services/agent/tools/gateway_api.py).

**Frontend**
- The Routines tab is a placeholder: `activeTab === 'routines'` in [src/App.tsx](../services/gateway/frontend/src/App.tsx), listed in `components/layout/Sidebar.tsx`.
- There's no router. Tabs are state.
- Mobile layout is a priority.

**Database**
- The schema comes only from Alembic (in `shared/`). The current head is in CLAUDE.md. New tables mean a reviewed autogenerated migration (see CLAUDE.md for the tunnel and autogenerate procedure).

## Design questions to answer (in the proposal)

1. **Where the scheduler runs.** The recommendation is an asyncio task inside the gateway, started in `lifespan`, since the gateway owns the MQTT bus and the twin. Consider instead a separate service. Constraints:
   - The Pi is small, and only one gateway process runs.
   - There's no hot reload.
   - The scheduler must survive a gateway restart: routines load from Postgres, and nothing important lives only in memory.
2. **Data model.**
   - Tables for routines (owner user, name, enabled, triggers, conditions, actions) and for a run log. Decide what is JSONB and what is columns.
   - The JSON shapes of triggers and actions should be validated with Pydantic.
   - Keep the shapes simple enough for the agent to create and edit routines later ("remind me... every weekday").
3. **Trigger types for v1.** At least:
   - time of day with days of the week
   - sunrise/sunset with an offset
   - a device state change, e.g. `contact` becomes `false`, or a value goes above or below a threshold

   Decide on debouncing (e.g. a motion sensor firing repeatedly) and catch-up rules after downtime: a 07:00 routine missed during a reboot should probably *not* run at 07:20, or only within a grace window.
4. **Conditions.** Time window, day of week, a device state equals or compares to a value, sun up or down.
5. **Action types.**
   - Deterministic, in-gateway: set a device, set a group, delay or wait. A "fade" could be a series of brightness steps or Z2M `transition`.
   - Spotify: the token logic lives in the agent. Options:
     - (a) a gateway→agent internal endpoint that runs a Spotify tool directly, with no LLM
     - (b) moving token refresh into `shared/`
     - (c) an "ask the agent" action that runs a natural-language instruction through the LLM loop

     Option (c) is flexible, but it costs tokens, can behave differently each run, and can fail silently. It may still be worth having as an explicit, clearly labelled action type.
6. **Reliability and observability.**
   - Every run records its trigger, each action's result and any error.
   - Show the last run status in the UI.
   - Decide whether failures surface anywhere beyond the UI.
7. **API and UI.**
   - CRUD endpoints, protected per route by `get_current_user`, plus "run now" and enable/disable.
   - A routine list and editor that works on mobile.
   - Decide whether routines are per-user or household-wide. There's no RBAC yet.
8. **Agent integration (later, but don't design it out).** Agent tools to list, create, enable and disable routines, so "turn off everything at midnight every night" works by voice or chat.

## Known issues to fold in

These matter more once nobody is watching:
- **Device `/set` replies** resolve on the device's next state publish from any source, and aren't matched against what was requested (see Known issues in CLAUDE.md). A routine would log "success" for a lost command. At minimum, match on `state` for on/off commands. Brightness and colour can't be matched reliably.
- **Group member removal** (KNOWN BUGS in [docs/todo.md](todo.md)): it sometimes targets the wrong group ID and makes MQTT throw. See `remove_group_member` and `delete_group` in `routes.py`, which call `zigbee2mqtt/bridge/request/group/members/remove`. Routines that use groups shouldn't hit this. It's worth reproducing and fixing first as a warm-up.
- The MQTT listen loop must keep catching per-message exceptions. A scheduler subscribing to the bus must not be able to kill it.

## Constraints

- **Keep it lightweight.** The Pi also runs Pi-hole, Tailscale, Mosquitto, Z2M, Soloist and the whole compose stack. Don't add heavy dependencies; a small, pure-Python library is fine if it earns its place.
- **There are no tests.** Verify per CLAUDE.md:
  - `uv run python -m compileall -q services shared`
  - `npx tsc -b` in the frontend
  - Rebuild the container and read the logs.
- **Don't push, deploy to the Pi, run migrations on the Pi, or change the Pi over SSH without asking.** Read-only SSH checks are fine.
- **Never print or commit secrets** from `.env` or the database.

## Working notes from the previous session

- **PowerShell 5.1 strips nested quotes** in `ssh host '...'` commands. For anything interactive or quote-heavy, ask me to SSH in and run it in the Pi's bash. Or write a script locally, `scp` it over, and run it there.
- **Don't use `pkill -f <pattern>` over SSH.** It can match and kill the SSH session's own command line. Use `pgrep -x` or `pkill -x`.
- **To run code against the real DB and Spotify tokens without printing secrets,** copy a script into `home_agent` and run it with `docker exec -w /app/services/agent home_agent uv run --no-sync python /tmp/x.py`. Print only names and states, then delete the script.
- **`docker compose run` without a TTY needs `-T`,** or use `-d`.
